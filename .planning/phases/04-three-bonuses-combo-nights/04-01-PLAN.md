## Phase Goal

**As a** portfolio visitor playing HOTLINE, **I want to** have each phone deliver its Witch Pots-style feature and see multi-phone triggers run as an ordered combo night (including nesting during free spins where config allows), **so that** I feel the full Witch Pots bonus loop of three bonuses including combos in Hotline Miami dress.

<objective>
**As a** portfolio visitor, **I want** a green phone trigger to open a real free spins night with splash, auto-run spins, and exit total, **so that** BONUS-01 plays end to end and the combo night machine (BONUS-04) is the proven primary path.

Purpose: Production-quality tracer from config through a pure night machine, HotlineGame free spins, a DOM splash overlay, and a session presenter. It lands the two costly decisions first: D-05 retrigger odds in the feature math contract and D-17 pause and resume of free spins around nested features.
Output: Phase 4 config contract; freeSpins math; createNight; HotlineGame night API; FeatureOverlay splash; session night presenter replacing the Phase 3 stub drain; Vitest coverage for order, nesting, retrigger cap, accounting, stream isolation.
</objective>

<precondition>
Phase 3 is complete: HotlineGame.spin returns collectorOutcome with an ordered queue, and mountHotlineSession drains it through the present stub phase.
</precondition>

<assumption_delta_decision>
Detector: pluralization, term "multiple" (multiple phones trigger, ordered combo).
Decision: **promote**
Rationale: The combo night becomes the primary play path. createNight owns queue order, the suspended free spins frame, the nested queue, the path, and win accounting. A single feature is a one-entry night through the same machine, not a separate code path. The Phase 3 stub drain is removed, not kept beside the night presenter. No second Pixi Application and no parallel game object: the night lives inside the existing HotlineGame.
</assumption_delta_decision>
